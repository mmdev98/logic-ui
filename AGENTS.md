# AGENTS.md

Shared rules for every coding agent working in this repo: Claude Code, Codex, Cursor, Junie, GitHub Copilot, Gemini CLI, Windsurf, Aider, and any other tool that reads `AGENTS.md`.
This is the only file to edit. `CLAUDE.md` only points here.
Put rules for a single folder in an `AGENTS.md` inside that folder.

## What this repo is

`@logic-ui/react` is a library of **headless React primitives**: components and hooks that handle
behaviour and accessibility (state, keyboard, focus, ARIA) and render **no styles**. It has two layers:

1. **Base UI re-exports.** Every public `@base-ui/react` entry point is re-exported under the same
   path (`@logic-ui/react/dialog`), plus a curated set of hooks from `@base-ui/utils`
   (`@logic-ui/react/utils`). Apps import from this package only, never from `@base-ui/*` directly.
2. **Our own primitives** for what Base UI doesn't have (`Clipboard`, …). They follow Base UI's API
   so they feel the same: a `render` prop, `data-*` state attributes, `value` / `defaultValue` /
   `onValueChange`.

```text
.
├── packages/
│   └── react/               @logic-ui/react, the published package
│       ├── src/<component>/ one folder per entry point
│       ├── scripts/         generate-exports.mjs
│       └── test/            Vitest setup and shared helpers
└── apps/
    └── docs/                docs site (Next.js + MDX); also where demos are tried
```

## Commands

- Package manager: `pnpm` 12 (pinned in `packageManager`). Node 24+. pnpm settings such as
  `allowBuilds` live in `pnpm-workspace.yaml`, not in `package.json`.
- From the root: `pnpm dev` (docs at http://localhost:3005), `pnpm build` (the library),
  `pnpm docs:build` (static docs export), `pnpm typecheck` (library and docs), `pnpm lint`, `pnpm test`,
  `pnpm format`. Root scripts run through turbo.
- In `packages/react`: `pnpm generate:exports`, `pnpm vitest run <path>`.
- Don't run `pnpm test:watch` or plain `vitest` from an agent: watch mode never exits.

## Verifying changes

Before you say a change is done, or before a commit:

1. Run `pnpm typecheck`, `pnpm lint` and `pnpm test` from the root. If you touched the build, the
   exports or a public type, also run `pnpm build`.
2. Read the diff and check it against the rules in this file.
3. Report each check as passed or failed with the real output. Don't claim a check passed if you didn't
   run it. Fix failures your change caused; report failures that were already there.

## Base UI re-exports

- `src/<entry>/index.ts` files that start with `// @generated by scripts/generate-exports.mjs` are
  written by the script. **Don't edit them by hand.**
- After upgrading `@base-ui/react`, or after adding, renaming or removing a component folder, run
  `pnpm generate:exports`. It writes the missing re-export folders and rebuilds `exports` in
  `package.json`. Never edit `exports` by hand; commit the regenerated file with the change.
- **Replacing a Base UI component with our own version:** delete the generated `index.ts` in that
  folder and write the component there. The script skips folders without the marker, so ours wins.
  Keep Base UI's part names and props so the swap is not a breaking change.
- `@base-ui/react` is a **dependency**, pinned to an exact version. This package replaces Base UI in
  apps: they install only `@logic-ui/react` and never add `@base-ui/react` themselves, so there
  is one copy and contexts work. `tsdown` keeps dependencies external, so `build` imports it instead
  of bundling it. Upgrading Base UI means bumping this pin, and `@base-ui/utils` with it.
- `@base-ui/utils` is a **dependency** too, pinned to the exact version `@base-ui/react` uses, so pnpm
  installs one copy. It is still 0.x: re-export a helper from `src/utils` only when our components
  rely on it, and check its signature after every upgrade.
- Don't re-export `@base-ui/react/internals/*`. It is private API and changes without notice.

## Writing a primitive

### Rules

- **No styles.** No CSS files, no `className` or `style` defaults, no Tailwind, no CSS-in-JS. Expose
  state as `data-*` attributes and let the app style it.
- **No app dependencies.** No i18n library, router, data fetching or framework imports (`next/*`).
  Text comes from `children` or props. A primitive renders no visible text of its own, except
  ARIA labels that the caller can override.
- **Build on Base UI's tools.** Render every part with `useRender` from `@base-ui/react/use-render`,
  merge internal and caller props with `mergeProps` from `@base-ui/react/merge-props` (event handlers
  are chained, the caller's other props win), and use `@base-ui/utils` for `useControlled`,
  `useStableCallback`, `useTimeout`, `useMergedRefs` and `useIsoLayoutEffect` instead of writing new ones.
- **Accessibility is part of the primitive.** Set roles, ARIA attributes and keyboard handling
  inside the parts. Follow the matching [WAI-ARIA pattern](https://www.w3.org/WAI/ARIA/apg/patterns/)
  and test it.
- **Look at Base UI first.** Before writing a new primitive, check whether Base UI has it or a part
  you can compose. The fork in `D:\dev\forks\base-ui` is the reference for structure, tests and
  edge cases: read the matching component in `packages/react/src` before inventing an API.
- **SSR-safe.** Don't touch `window`, `document` or `navigator` during render. Use them in effects or
  event handlers, and use `ownerDocument`/`ownerWindow` from `src/utils` for elements in iframes.
- **No side effects at import.** The package sets `"sideEffects": false`.
- **Keep parts pure.** A part doesn't read the route, global stores or other app-wide state to change
  its behaviour. Everything comes in through props, so every app can use it the same way.

### Moving a component from an app

When an app component (for example from `gestionhelicos-frontend/src/components/`) moves here, split
it in two:

- **Here:** state, keyboard, focus, ARIA, gestures and the parts, written with the rules in this file.
- **In the app:** a thin styled wrapper that composes these parts with its Tailwind classes, `cva`
  variants, theme tokens, icons and translated labels. It styles the parts through their `data-*`
  attributes (`data-open:opacity-100`, `group-data-zoomed:…`), never by reading state from outside.

Keep the app component's part names and props where they already follow these rules, so the app
only changes imports. Rename the ones that don't, and list the renames in the commit body. Rewrite
everything else to follow these rules, including code the app marks as legacy.

### Folder layout

The layout follows Base UI (`packages/react/src/slider` in the fork), with kebab-case names. One
folder per entry point, named after the component, and in it **one folder per part**, named after
the part. `src/clipboard` is the small reference, `src/lightbox` the large one.

```text
src/lightbox/
├── root/
│   ├── lightbox-root.tsx                   the part
│   ├── lightbox-root.test.tsx              its tests
│   ├── lightbox-root-context.ts            the context it provides
│   └── use-lightbox-zoom.ts                a hook only this part uses
├── popup/
│   ├── lightbox-popup.tsx
│   ├── lightbox-popup.test.tsx
│   ├── lightbox-popup-data-attributes.ts   its `data-*` attributes, documented
│   └── lightbox-popup-css-vars.ts          the CSS variables it sets, documented
├── trigger/ viewport/ slide/ media/ …      one folder per part, same shape
├── utils/
│   ├── lightbox-geometry.ts                pure helpers, grouped by topic
│   └── lightbox-geometry.test.ts
├── constants.ts                            LIGHTBOX_ZOOM_SCALE …
├── types.ts                                value types and enums shared by the parts
├── use-lightbox-action.tsx                 hooks shared by several parts
├── test-utils.tsx                          test helpers shared by the part tests
├── index.parts.ts                          parts under their short names
└── index.ts                                namespace + full names, hooks, types, constants
```

- A part's folder holds everything that belongs to that part only: its file, test, context, data
  attributes, CSS variables and private hooks. Files shared by several parts sit at the component
  root; pure helpers go in `utils/`.
- Import across part folders by exact path (`../root/lightbox-root-context`), never through `index.ts`.
- `index.parts.ts` re-exports the parts under their short names (`export { ClipboardRoot as Root }`).
- `index.ts` exports the namespace first (`export * as Clipboard from "./index.parts"`), then the full
  names, context hooks, value types, props types, state types, enums and constants, and the data
  attribute and CSS variable docs as namespaces
  (`export * as LightboxPopupDataAttributes from "./popup/lightbox-popup-data-attributes"`). Hooks and
  types are never namespace members: `useClipboardRootContext`, not `Clipboard.useRootContext`.
- Add the folder to `src/index.ts` (`export * from "./clipboard"`), then run `pnpm generate:exports`.
- Put `"use client"` at the top of every part, context and hook file, not in `index.ts` or
  `index.parts.ts`, so the namespace also works from React Server Components. `tsdown` builds with
  `unbundle`, one output file per source file, so the directive stays at the top of each file.

### Parts

A component made of parts is used as `<Clipboard.Root>`, `<Clipboard.Trigger>`. Name each part with
one noun from the Base UI vocabulary, so the same word means the same role everywhere:

| Part                              | Role                                                                |
| --------------------------------- | ------------------------------------------------------------------- |
| `Root`                            | Holds the state and provides the context. Renders little or nothing |
| `Trigger`                         | Opens, toggles or starts something                                  |
| `Portal`, `Backdrop`, `Popup`     | Overlay layers                                                      |
| `Viewport`, `List`, `Item`        | Scroll area, collection, one entry                                  |
| `Title`, `Description`, `Label`   | Text that names or explains, linked for accessibility               |
| `Value`, `Icon`, `Indicator`      | Current value, decorative icon, state marker                        |
| `Close`, `Increment`, `Decrement` | Actions: a verb or noun, without a `Button` suffix                  |
| `Group`, `Separator`              | Grouping and dividers                                               |
| `Preset`                          | Ready-made composition of the parts (our addition)                  |

Add a domain noun only when no Base UI word fits (`Lightbox.Slide`, `Lightbox.ZoomIn`,
`Lightbox.Caption`). A component with a single part stays a plain export (`ZoomPan`), with no namespace.

A `Preset` composes the parts for the common case so the caller writes one element instead of five.
It stays headless like every part, and the parts remain the way to build anything it doesn't cover.

### Names and types

- The component is `<Component><Part>` (`ClipboardRoot`, `LightboxZoomIn`) in
  `<part>/<component>-<part>.tsx` (`zoom-in/lightbox-zoom-in.tsx`), one part per file like Base UI.
- Props are `<Component><Part>Props`; build them on Base UI's helper:
  `interface ClipboardRootProps extends useRender.ComponentProps<"div", ClipboardRootState>`.
  Use a `type` alias instead of an empty `interface … extends`.
- State is `<Component><Part>State` and **must be a `type` alias, not an `interface`**:
  `useRender` needs the implicit index signature that only type aliases have.
- An imperative API goes through a `ref` with a `<Component>Handle` type (`ZoomPanHandle`).
- **No TypeScript namespaces** (ESLint enforces it). Write `ClipboardRootProps`, not
  `ClipboardRoot.Props`. Using Base UI's namespaces (`useRender.ComponentProps`) is fine.
- **Explicit return types** on every exported function, component and hook
  (`: React.ReactElement`, `: React.ReactElement | null`, `: ClipboardRootContextValue`). The public
  `.d.ts` files depend on them, and JSR rejects inferred public types.
- Write a JSDoc comment on every part (what it does, which element it renders) and every prop. Put
  defaults in `@default`.

### Props and state

- Destructure props in the body: `export function ClipboardRoot(props: ClipboardRootProps) { const { value } = props; }`.
  Pull out `render` and `ref`, pass them to `useRender`, and spread the rest through `props`.
- Boolean props and state fields have no prefix, like HTML: `open`, `disabled`, `pending`, `copied`
  (local variables, context values and helpers keep `is`/`has`/`can`).
- A value the caller may control comes as `value` / `defaultValue` / `onValueChange`, named after the
  value: `open` / `defaultOpen` / `onOpenChange`, `index` / `onIndexChange`. Implement it with
  `useControlled`. Add `on<Value>ChangeComplete` for the end of an animation.
- Don't reuse a DOM event name for something else. `onCopy` already means the native copy event, so
  the clipboard callback is `onCopiedChange`.
- Expose state for styling as `data-*` attributes through `useRender`'s `state`. Boolean state
  becomes `data-copied` when `true` and is absent when `false` (`data-open`, `data-disabled`,
  `data-pending`, `data-zoomed`). Apps style with data variants (`data-zoomed:cursor-grab`) instead of
  reading state from outside.
- Document every `data-*` attribute a part sets in `<part>/<component>-<part>-data-attributes.ts`, and
  every CSS variable in `<part>/<component>-<part>-css-vars.ts`, one exported constant each with a JSDoc
  comment, like Base UI's `SliderThumbDataAttributes.ts`:

  ```ts
  /** Present while the image is zoomed in. */
  export const zoomed = "data-zoomed";
  ```

- Every part accepts `render` (an element or a function `(props, state) => element`) so the caller
  can change the element or compose another component. To combine a part with another component's
  part, put the part that owns the behaviour outside:
  `<Lightbox.Next render={<Toolbar.Button />} />`, not `<Toolbar.Button render={<Lightbox.Next />} />`.
  The outer part's props are merged last, so the inner one would lose its `disabled`. Don't add
  a container part that only wraps a Base UI one (a `Lightbox.Toolbar`): compose Base UI's.
- Inline styles are allowed only where the behaviour needs them: positions and transforms written
  by a gesture, `touch-action`, `overflow` that clips a zoomed image. Never set a size, colour or
  position the app could choose. Leave layout (`position: absolute; inset: 0`) to the app's CSS.
- A part that only shows when some state is on (`Indicator`) renders `null` otherwise, and takes
  `keepMounted` to stay in the DOM.

### Contexts and hooks

| What               | Name                            | Example                     |
| ------------------ | ------------------------------- | --------------------------- |
| Context            | `<Component><Part>Context`      | `ClipboardRootContext`      |
| Its value type     | `<Component><Part>ContextValue` | `ClipboardRootContextValue` |
| Hook that reads it | `use<Component><Part>Context`   | `useClipboardRootContext`   |
| File               | `<component>-<part>-context.ts` | `clipboard-root-context.ts` |

- Name the context after the part that provides it (`ClipboardRootContext`, not `ClipboardContext`).
- Create it with `null` as default: `createContext<ClipboardRootContextValue | null>(null)`.
- Read it only through its hook, never `use(XContext)` in a part. The hook uses React 19 `use()` and
  throws when the provider is missing (see _Errors_ below). When the context is optional (a `Toggle`
  outside a `ToggleGroup`), the hook returns `… | null` instead and says so in its doc comment.
- Provide it with `<XContext value={value}>`, not `XContext.Provider`, and don't export aliases like
  `export const XProvider = XContext.Provider`. The part that owns the state provides it.
- Memoize the value with `useMemo`; make its functions stable with `useStableCallback` (there is no
  React Compiler). Like Base UI: `useStableCallback` for functions called from effects and event
  handlers, `React.useCallback` for functions called during render (such as a ref callback).
- Put values that change every frame (pointer position, zoom level) in a second context named
  after what it holds (`LightboxRootZoomContext`), so parts that don't need them don't re-render.
  Put stable callbacks in `<Component><Part>ActionsContext` when many parts only need those.
- Export the hook and the value type. Export the context itself only when another file has to
  provide it.
- A hook is `use<Component><Purpose>` in `use-<component>-<purpose>.ts`, one exported hook per file
  (`use-lightbox-element-ref.ts` exports `useLightboxElementRef`). It lives in the folder of the
  component that uses it.
- Its options object is `Use<Hook>Options` and its named return type `Use<Hook>Result`. Positional
  arguments are fine for one or two values.
- Only hooks start with `use`. A plain function that happens to run in a component is not `useX`, and a
  hook is never called conditionally.

### Utils

Pure, single-purpose functions named `<verb><Component><Purpose>` (`clampLightboxZoom`,
`getLightboxItemIndex`), in the component's `utils/` folder, grouped in files by topic
(`lightbox-geometry.ts`) with a test file next to each. Booleans start with `is`, `has`, `can` or
`should`.

- Use the browser through Base UI's helpers, as Base UI does: `useTimeout` / `Timeout` instead of
  `setTimeout`, `useAnimationFrame` / `AnimationFrame` instead of `requestAnimationFrame`,
  `ownerDocument` / `ownerWindow` instead of the globals.

### Errors

Every error a part throws says what happened, why it's a problem and how to fix it, prefixed with
`Base UI:`, like Base UI's messages:

```ts
throw new Error(
  "Base UI: LightboxRootContext is missing. " +
    "Lightbox parts must be placed within <Lightbox.Root>.",
);
```

### Constants and enums

- Fixed module-level values are `SCREAMING_SNAKE_CASE` with the component prefix
  (`CLIPBOARD_DEFAULT_TIMEOUT`) in `constants.ts`, and they are exported.
- Use a TS `enum` for a closed set of values (`enum ZoomPanMode { Pan = "pan" }`), not a string union.

## Tests

Vitest, Testing Library and jsdom. The rules follow Base UI's (`AGENTS.md` in the fork).

- Each part is tested in `<part>/<component>-<part>.test.tsx`, next to it; each `utils/` file has
  its own `.test.ts`. A test belongs in the file of the part whose prop or behaviour it asserts.
  Put a composition the part tests share in the component's `test-utils.tsx`.
- Cover at least: the default element and its ARIA attributes, each state through its `data-*`
  attribute, controlled and uncontrolled use, keyboard interaction, the `render` prop keeping the
  caller's handlers, `keepMounted`, error paths, and the error thrown outside `Root`.
- Query by role and text (`getByRole("button")`), not by class or test id, except on parts with no role.
- Mock browser APIs that jsdom doesn't have (`navigator.clipboard`, `ResizeObserver`) in the test
  file, reset them in `beforeEach`, and restore real timers in `afterEach`.
- Wrap anything that resolves a promise in `await act(async () => …)`.
- A test must be able to fail when the behaviour in its title breaks: assert the starting state
  before the action when the end state could already hold, and break the behaviour once to see the
  test fail.
- One assertion per `waitFor`. Never put a negative assertion in `waitFor` (it passes on the first
  poll): flush or advance timers first, then assert.
- Use `it.each` for cases that differ only in data, not tests registered in a loop.
- jsdom has no layout, Web Animations or real touch. Check gestures, measurements and animations in
  the docs too (`pnpm dev`), and say in the report what was checked in a browser.

## Docs

`apps/docs` is our own docs site (Next.js, MDX, Tailwind, Shiki), dark only. It documents our
primitives in full and lists the Base UI re-exports with links to base-ui.com. It is also where demos
are tried by hand: there is no separate playground.

- It reads the library from `packages/react/src` through tsconfig `paths`
  (`"@logic-ui/react/*": ["../../packages/react/src/*"]`), so it needs no build. Don't
  change it to read `build`.
- It follows the repo's ESLint, Prettier and code style, like the package. Class names are merged
  with `cn` (from the `cn` package), not `clsx`.
- **Pages.** `src/nav.ts` is the one list of pages (slug, title, description, MDX file, `api`). The
  sidebar, routes, search and llms.txt all read it. A page is an MDX file in `src/content`, loaded
  through `src/content/pages.ts`. The title and description come from `nav.ts`, so the MDX starts
  with the content.
- **A page per primitive.** Add `src/content/components/<component>/index.mdx` and its demos in
  `demos/<example>.tsx`, Tailwind only. Classes several demos share go in `demos/_classes.ts`.
  Demos are the only styled code.
- **Demos.** Write `<Demo src="./demos/grid.tsx" />`. The `remark-demos` plugin
  (`src/pipeline`) imports the file and passes its path. `Demo` renders it and shows its source and
  the local files it imports, highlighted with Shiki at render time.
- **API tables.** Write `<ApiReference component="lightbox" parts={["Root", "Trigger"]} />` on one line
  (`parts` is optional and sets the order). `src/lib/api.ts` reads the parts, their props and JSDoc,
  the `*-data-attributes.ts` and `*-css-vars.ts` files next to each part, and the value types and
  enums exported from `index.ts`, with the TypeScript compiler API. So the JSDoc rules above are
  what the docs show.
- **Search and llms.txt** are static routes built from the same MDX: `/search-index.json`,
  `/llms.txt` (an index linking each page's Markdown) and `/md/<slug>.md`.
  `src/lib/markdown.ts` turns a page into Markdown.
- The docs track nothing and send nothing: no analytics, no feedback endpoint. Keep it that way.
- `next dev` writes `apps/docs/AGENTS.md` with Next.js notes. Leave it.

## Code style

- Everything in code is in English: names, comments, tests, commit messages.
- Files and folders are kebab-case. Components are PascalCase and named after their file.
- Import React as `import * as React from "react"` in components, like Base UI.
- Inside the package, use relative imports only. No path aliases: they don't survive publishing.
- Don't import from the package's own barrels (`src/index.ts`, a folder's `index.ts`) inside `src`.
  Import the exact file (`./clipboard-root-context`) to avoid import cycles. Tests may import their
  folder's `index.ts`.
- Prettier formats everything. Don't fight it.

## Versioning and publishing

- The package follows semver. Until `1.0.0`, a minor version (`0.x.0`) may break the API; say so in
  the changelog.
- **Breaking changes** include renaming or removing a part, prop, `data-*` attribute or export path,
  changing a default, and raising the minimum `@base-ui/react` or React version.
- A Base UI upgrade that changes a re-exported API is a breaking change for us too. Read its
  changelog and mention what changed.
- The published package is `build/`, flat like Base UI's: `dialog/index.js` at the root, not
  `build/dialog/index.js`. `pnpm build` runs `tsdown`; after the build, `tsdown.config.ts` writes
  `build/package.json` (exports without `./build/`, no `scripts` or `devDependencies`) and copies
  the README and LICENSE. `publishConfig.directory` makes `pnpm pack` and `pnpm publish` pack
  `build/`. Edit the root `package.json` only; `build/package.json` is generated.
- To try the package in an app before publishing: `pnpm build`, then
  `pnpm pack --pack-destination <absolute path>` from `packages/react` (pnpm resolves a
  relative path from `build/`), and install the `.tgz` in the app with `pnpm add <path to .tgz>`.
- The changelog is the docs page `apps/docs/src/content/changelog.mdx`, newest release first.
- Release steps: `pnpm build && pnpm test`, bump the version in `packages/react/package.json`,
  add its entry to the changelog, then `pnpm publish` from `packages/react`. Publish only when
  asked.

## Commit messages

Format: `[scope] Subject`, optional body after a blank line. Always in English.

- **Scope**: one lowercase kebab-case name for the main thing the commit changes: the component
  (`clipboard`, `zoom-pan`) or one of these global scopes:

  | Scope        | For                                                |
  | ------------ | -------------------------------------------------- |
  | `base-ui`    | Re-exports and `@base-ui/*` upgrades               |
  | `utils`      | `src/utils` re-exports and shared helpers          |
  | `deps`       | Adding, updating or removing other packages        |
  | `build`      | `tsdown`, `exports`, `generate-exports.mjs`, turbo |
  | `code-infra` | ESLint, Prettier, TypeScript config, Vitest setup  |
  | `infra`      | CI (GitHub Actions), publishing                    |
  | `release`    | Version bumps and changelogs                       |
  | `docs`       | The docs site (`apps/docs`) and README             |
  | `ai`         | `AGENTS.md`, `CLAUDE.md` and other agent config    |

- **Subject**: imperative, capitalized, no trailing period, at most ~72 characters. Describe what
  changes for the user of the library: ``Add `keepMounted` to `Clipboard.Indicator` ``, not
  `Update indicator file`. Put identifiers and package names in backticks.
- **Dependencies**: one package per commit, `` [deps] Update `vitest` to `5.1.0` ``.
- **Body**: add one when the reason isn't obvious from the subject. Wrap at ~72 characters, plain
  sentences, `-` lists for several separate changes. Mark breaking changes with a `BREAKING:` line.
- Commits written with an AI agent end with that agent's `Co-Authored-By:` trailer.
- **Splitting**: one commit per separate change. Stage by path. Never commit `build`, `dist`, `.turbo`,
  `*.tsbuildinfo` or `.env*`.
- Never use `--no-verify`. Don't push or publish unless asked.

```
[clipboard] Add `Clipboard` primitive

Root holds the copied state and resets it after `timeout`. Trigger
copies the value, and Indicator renders only while copied. All parts
expose `data-copied`.
```
